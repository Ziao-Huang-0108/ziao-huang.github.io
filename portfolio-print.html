01 · Problem

项目背景：多人吃饭，为什么这么难？

面对「吃什么」，很多人会说「随便」，把决定权交给别人，或只给出「不太能吃辣」之类的模糊范围。 多人一起时，需求还可能冲突；选得不好，做决定的人容易承担额外压力。

美团、大众点评、小红书更擅长帮用户拿到餐厅列表。 用户仍要从大量候选里自行了解并做最终决定，也很难同时结合多人不同需求。 对选择困难的人来说，即使一个人吃饭也可能卡住。

Core question 问题不是「找不到餐厅」，而是面对大量选择时，很难快速找到一个大家都能接受的答案。 当选择很多、需求又有差异时，如何帮助用户完成一次「可接受」的用餐决策？

02 · Goal

产品目标与定位

把「找餐厅」升级为「帮用户做决定」，验证四个方向：

个性化 · 成员档案

多成员偏好、忌口与历史反馈可组合进一次推荐。

需求理解

把偏好与忌口变成可用于推荐的结构化条件。

推荐可解释

展示推荐依据与评分构成，让用户知道「为什么是这家」。

反馈闭环

用餐后评分回写到具体成员，影响后续推荐。

Positioning 核心目标不是预测「用户最喜欢哪一家」，而是在多人、多种需求下做优先级排序与协调，快速给出可接受结果。 相对美团 / 点评：它们已有真实餐厅数据库；本项目更接近平台可增加的一层决策 / 推荐能力，而不是从零搭一套餐饮 App。 产品做成免登录、点开即用，降低试用成本，也符合「能力层」该有的轻入口。

03 · Solution · Flow

产品方案：逻辑一览

选成员 + 场景 / 距离合并偏好、忌口与历史评分
↓
硬过滤忌口命中即淘汰；距离无结果则放宽
↓

↓

↓
有命中只在偏好子集内排序
无命中退回全候选再排序
↓
可解释结果 → 打分反馈评分写入对应成员记忆，供下次推荐

03 · Solution · Design

可组合档案 · 硬约束 vs 软偏好

3.1 可组合的成员档案

吃饭天然多人，因此没有做成单一用户画像，而是可组合的成员档案： 同一个人跟不同的人吃饭，参与决策的需求组合也不同。每次勾选实际成员，合并偏好、忌口与历史评分后再进入推荐。

3.2 硬约束 vs 软偏好

硬约束（如过敏、最大距离）不能违反； 软偏好（如「想吃火锅」）尽量满足，但不意味着其他类型绝对不能推。

3.3 三层优先级（不全混在一个加减分里）

因素层级行为
忌口 / 过敏硬约束命中即淘汰
最大距离硬约束（可放宽）先按范围过滤；空则放宽
历史 1–2 星排除任一成员差评 → 不进排序池
饮食偏好软门控有命中 → 子集排序；无命中 → 退回全候选
场景 / 星级 / 历史好评评分在候选池内打分；同分随机
用餐人数仅展示不参与硬淘汰（测试后调整）

推荐机制比「记一张清单」更重：召回与排序必须对齐目标，否则链路会整体失效——这也是后面要做更多测试的原因。

05 · Testing · 01–03

测试与打脸：假设要被结果纠正

推荐链路一复杂，就不能只靠直觉认功能「合理」。我用构造场景做了多轮测试，并补上 Usage Log / Debug，让异常结果可复盘。

01

用餐人数不应成为硬限制

「一人食 + 想吃火锅」时，火锅店因适用人数不含 1 人被直接滤掉。调整：人数改为参考信息，不再硬淘汰。

02

看起来周全的输入可能完全没用

「交通方式」改了，推荐却不变——字段没进逻辑。调整：删掉该输入。只有能改变决策结果的变量，才值得增加输入成本。

03

记忆数据到底属于谁

成员 A 的五星评分影响了只选成员 B 的推荐。根因是历史记忆按浏览器全局存，没绑到档案。调整：评分严格归属成员。这是产品数据建模问题，不只是存储 Bug。

05 · Testing · 04–05

测试与打脸（续）

04

当下需求应优先于历史偏好

同时有人历史爱泰国菜、有人当前想火锅时，系统先推了泰国菜。调整：降低历史权重，把本次偏好前置到召回。过去喜欢什么，不能盖住这次想吃什么。

05

召回对了，排序目标仍可能错位

第二轮构造多人冲突场景：火锅进了候选池，但最终排序仍被其他类型压过——偏好只缩了候选，池内打分未体现群体偏好满足度。 启示：推荐要同时做好「哪些店能进来」和「进来后优先推谁」，两者目标不一致，整条链路会失效。

Why more testing here 相对 Remember Me，本项目的逻辑中心是推荐机制，错误更隐蔽，所以测试密度更高：人工场景 → 可观测日志 → 冲突场景复盘。 做下来最深的体会是：要用结果打脸假设，而不是把「功能做完」当成验证完成。

06 · Future

未来优化方向

真实位置
  • 当前用预设 / 模拟距离做硬过滤，距离是「离我多远」的单点近似。
  • 局限多人吃饭时，真正的问题往往是「对大家都方不方便」，不是只服务某一个人的坐标。
  • 未来接入地图 / 定位，收集多成员位置，优先推对全体出行更友好的中间地带餐厅。
菜品级匹配
  • 当前推荐对象停在餐厅：类型、场景、忌口都按店级标签处理。
  • 局限店适合某人，不等于每道菜都适合；海鲜过敏仍可能在店里吃到安全选项。
  • 未来接入菜单信息，按菜品考虑过敏、饮食限制与营养，形成「餐厅 → 菜品 → 成员」匹配。
群体满意度
  • 当前主要按单店综合适配度排序；偏好更多影响「谁能进池」。
  • 局限多人偏好都进了候选，最终仍可能更偏向其中一人，群体满足度不显式。
  • 未来把「满足了多少人的核心需求、有没有人完全吃不了」写进排序，并支持分成员反馈。

07 · Reflection

项目收获

01

现实里合理的因素（人数、交通），放进产品不一定该做约束；要用测试验证。

02

推荐不只是算分：数据归属、需求优先级、可解释性、召回与排序对齐，都是产品设计。

03

功能跑通 ≠ 产品闭环；核心操作在真实页面上必须可点（结果页滚动曾挡住按钮）。

04

整理本项目复盘时大量翻聊天记录，成本很高——这也直接推动了下一个项目从第一天就写开发日志。

一个功能看起来合理，并不代表它真的有用。只有通过使用、观察结果、再改产品，才能知道最初的想法是否成立。

01 · Problem

项目背景：家里的东西，为什么总对不上？

家里东西越买越多，常见几种遇到的情况：

  • 忘了放在哪：钥匙、首饰、衣物等，要用时翻遍柜子。
  • 过期了才发现：药品、调料、护肤品、零食等放着放着只能扔掉。
  • 重复购买：不知道还有存货，又买了一份。
  • 信息不共享：某一个人购买、存放的，其他家人不知道。
Core question 如何让一家人用同一份「物品小本子」，在需要时快速知道东西在哪、急不急处理， 同时又把家庭私密信息关在可控制的访问范围里？

02 · Goal

产品目标与定位

目标用户按角色拆开，避免做成「只有采购者爱用」的记事本：

角色特点主要需求
采购者会主动录入录入要快，操作简单
使用者很少录入，偶尔查找能快速搜到东西在哪
Positioning 相对「今天吃什么」：那个项目更像美团 / 大众点评等已有的平台可增加的决策能力层，而作为网页可以免登录点开即用。 Remember Me 要管的是家里私人物品与过期信息，需要家庭成员身份与家庭边界，因此更像独立 App 的雏形： 登录、家庭空间、云端同步、过期行动提示，都是产品本身，而不是外挂功能。

03 · Solution · Access

3.1 访问与形态：为什么要登录

「今天吃什么」可以免登录，因为试用成本低、数据敏感度相对较低。 Remember Me 记录的是药品位置、家用存货等家庭私域信息，不能做成谁打开都能看的公开页，所以必须登录。

当前访问策略

为了安全性和稳定性，不开放网页自助注册。账号只在我这边开通：只有我配置过的账户+密码可以进入。这是家庭小范围试用阶段的取舍，并非漏做注册。

形态选择

手机网页（PWA）+ CloudBase：不用上架审核，一个链接就能分享；可添加到主屏幕。后端用腾讯云 PostgreSQL，国内访问更稳。

03 · Solution · Fields & Color

3.2 记什么 · 3.3 过期颜色

字段为行动服务

每件物品记录名称、价格、功能/用途、购买日期、过期日期、放置位置、备注、照片与类别。 清单默认按「谁最先过期」排在前面——核心问题是「什么该先处理」，不是「最近买了什么」。

过期颜色：一眼能懂的信号

剩余天数 d颜色行动含义
d ≤ 30红马上处理
30 < d < 180橙近期留意
180 ≤ d < 365黄心里有数
d ≥ 365绿不用操心
已过期深红 + 过期天数单独一档，优先处理

同一档内越接近过期颜色越深。剩余天数不靠定时任务「每天刷新」，而是打开时用过期日减今天现算，数字永远跟日历走。

03 · Solution · Find & Home

3.4 查找与家庭

支持按过期情况、类别筛选，以及按名称 / 位置 / 备注关键词搜索。 一人可加入多个家庭并切换——对应「以后住别处仍要看旧家物品」的真实场景。

04 · Iteration · 01–03

迭代与洞察

相对「今天吃什么」里更重的推荐测试，Remember Me 的迭代主要来自自己在使用中的观察和思考。 外部真实反馈目前明确可复述的只有一条。验证方式不同，不是偷懒，而是产品阶段与问题类型不同。

01

定位转折：从「我一个人用」到「全家一起用」

最早做成给自己用的管理个人物品的单机本子，数据只在本机。但生活在家庭中会用到很多家庭共用的物品，这些物品常常是一个人买、其他人找或者根本不知道这些物品的存在，直到过期了才被翻出来，造成了不必要的浪费。于是定位改成全家共用：字段、过期颜色、账号与家庭空间都按多人场景重定。

02

先把主路径做顺，再接云端

登录和云端可以后接，但这个产品的核心功能————记录物品信息（功能、放置位置、什么时候过期）必须先顺。先在本地把录入和清单做清楚，再做家庭同步。保质期快捷按钮少让人自己换算日历；排序默认「谁先过期」，更好地起到提醒作用。

03

自用观察驱动改版

自己试用觉得第一版页面设计太单调，删除和编辑的按键也不明显。于是加大触控区与类别标签，补上照片和排序筛选，让清单更一目了然、条目更好点击。界面放了家里柴犬小六的卡通形象，进门可播放我的歌《4am》（可静音），把「家庭」感做进进门体验；装饰不喧宾夺主。

04 · Iteration · 04–05

迭代与洞察（续）

04

共享落地时的平台约束

登录用用户名 + 密码，考虑到用户只有本家庭成员所以没必要接微信登录和短信。腾讯云不允许网页自助开号，就去掉注册入口，账号只在控制台开通。体验版只有 PostgreSQL，数据改走 SQL；前端从国内访问不稳定的 Vercel 迁到 CloudBase 静态托管，和后端同落腾讯云。

05

唯一外部交互反馈：按钮被挡住了

一位家庭成员在手机上试，发现音乐控件挡住了「保存」，电脑宽屏上看不出来。把保存改到底部主按钮，音乐改成可拖、可贴边的小钮。功能步骤没变，真机可用性过关。这也提醒了我这个产品的使用设备是手机，所以我在进行页面设计的时候应该考虑的是手机用户的使用体验。

04 · Iteration · 06–07

迭代与洞察（续）

06

自用提出：一家不够用，分类也不够找——多家切换 + 关键词搜索

自用发现以后可能会到别的城市生活，新家和旧家物品需要查看；东西多了单靠过期 / 类别不好找。于是支持一人多家（多家时先选家，顶栏可切换），并加关键词搜索（可与原筛选叠加）。库表本来就允许多家，这次主要改前端认家逻辑，没有改表结构。

07

默认域名能开着开着变成下载——排查后改成诚实说明

默认域名有时正常、有时出风险页、有时下载 index.html；电脑曾能开后一直下载，手机删快捷方式再输网址又恢复。是平台对未备案域名的策略，和打开方式、风险 Cookie 有关；经过尝试发现重传无效。短期解决方案是写清试用说明，根本解法是申请备案域名（目前正在申请中）。

05 · Method

过程方法：从翻聊天的痛苦，到开发日志 Skill

整理第一个作品集（今天吃什么）时，我需要翻大量对话才能拼出「当时为什么这么做」，过程很痛苦，也容易漏掉决策理由。

所以做 Remember Me 时，一开始就加了硬约束：每完成一步，就同时记录在开发日志中：做了什么、为什么、遇到什么问题、怎么解决、有没有反馈。 这份记录后来收成可复用的 Skill，让之后的项目默认带着「外人也能读懂」的过程资产，不需要事后再费力整理。

Why this matters 「今天吃什么」让我确认：复杂推荐必须靠测试验证假设。 Remember Me 则是在家庭私域与平台约束里，把工具真正做成可上线的形态，并把复盘方法固定下来。

06 · Future

未来优化方向

可点户型图
  • 当前位置靠文字字段 + 照片说明「放在哪」，清单和搜索已能按位置找。
  • 局限对不熟家里布局的人不够直观；平面图更贴「家庭本子」，但画图与维护成本高。
  • 未来把家（含柜 / 箱 / 桌）做成可点平面图来标位置；家不大且照片够用时后做。
小六语音入口
  • 当前记下、查找都靠点选与打字；小六形象主要承担家庭氛围，不承担输入。
  • 局限录入字段多时手机打字成本高；口语「帮我记一下药箱里的感冒药」更自然。
  • 未来点柴犬说话完成「记下」或「找东西」（背后分流即可）；先过语音识别与口语结构化。
备案自定义域名
  • 当前线上用 CloudBase 默认域名，可能出风险页或下载 index.html。
  • 局限和机型无关，和打开方式、风险 Cookie 有关；试用说明不得不写得很长。
  • 未来正在申请备案域名；绑上后去掉这层限制，链接可直接当正常网站分享。

07 · Reflection

项目收获

01

数据敏感度决定产品形态：私域信息就要登录与家庭边界；轻试用能力可以免登录。

02

平台约束会改产品设计：不能网页自助注册时，诚实改成「控制台开号 + 只登录」比留一个必失败的按钮更好。

03

上线约束也要写进产品说明：默认域名的风控和机型无关，和打开方式、风险 Cookie 有关；说不清就会误导试用的人。

04

真机反馈不可替代：一条「按钮被挡住」就足以推翻桌面上看起来合理的布局。

05

验证强度要匹配问题：推荐机制需要更多结构化测试；生活工具在早期可以主要靠自用观察，但要诚实写明证据边界。

06

过程资产本身也是作品：开发日志 → Skill，把第一次作品集的坑变成第二次的默认能力。

把家里的私域工具做成可上线的形态，比多堆功能更重要：约束要写进设计，说明要写给试用的人听懂。
